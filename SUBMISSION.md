## Reproducible run command

The single command below is genuinely self-sufficient: no separate download or
build step, no manually-prepared registry file. Given a batch file of
organisation numbers, it anchors identity via the live per-entity registry
API directly.

```bash
uv sync
uv run python scripts/run_competition_batch.py \
  --organisations companies.jsonl \
  --profiles-output out/profiles.jsonl --output out/envelopes.jsonl \
  --report out/report.json --run-id run-001 --expected-count 100
```

`companies.jsonl` is whatever batch the test harness supplies: one
`{"organisation_number": "..."}` object per line (JSONL, plain-text, or `.json`
are all accepted; see `read_organisation_inputs` in `src/norway_company_agent/batch.py`).

Verified at real scale: a fresh 100-company run with this exact command
(no `--bulk`, no pre-fetched files) completed in 2 minutes 2 seconds using
roughly 636 total HTTP requests and $0 in API cost, against a daily budget of
45 minutes, 2,000 requests, and $10. See `results/budget-verification.json`.

`--bulk <path>` remains available as an optional alternative (reads a
pre-built national registry CSV instead of live per-entity lookups), useful
mainly for very large one-off local test batches where it's faster, but it is
not required and is not part of the declared run command above.

By default the command also persists each day's profiles under
`.signalpost_state/` and reads them back on the next invocation to compute
real change detection (see "Daily operation" below). Pass `--no-state` to
disable this, or `--no-explanation` to skip the per-company synthesized
explanation field if a faster, leaner run is preferred.

## Daily operation

The challenge runs a recurring daily evaluation against a rotating batch of
companies, scored in part on "update correctly" (keeping profiles current).
Two capabilities exist specifically for that:

- **Change detection across runs**: each invocation saves its output profiles
  to `.signalpost_state/previous-profiles.jsonl`. The next invocation loads
  that file, and for any company it has seen before, computes a real diff
  (`src/norway_company_agent/refresh.py`'s `diff_profile`) and attaches it to
  that company's envelope under `changes`. A company seen for the first time
  gets an empty `changes` list, not an error. Verified: a same-day re-run of
  six real companies produced zero false-positive changes; a deliberately
  injected prior-value change was correctly detected and cited on the next
  run.
- **Per-company synthesized explanation**: every envelope carries an
  `explanation` field (a cited overview answer generated by the existing
  research-agent logic, not a new synthesis path), so the explanation exists
  in the actual submitted output, not only in an interactive tool nobody runs
  during an automated batch test.

## Open question for the organisers

`OUTPUT_CONTRACT.md` documents a minimal envelope shape (`organisation_number`,
`run{}`, `claims[]`, `evidence[]`, `changes[]`, `errors[]`, `operations{}`).
Our actual emitted envelopes, built on the organiser's own
`scripts/run_competition_batch.py`, use a different top-level shape (`run_id`,
`organisation_number`, `state`, `started_at`, `completed_at`, `modules{}`,
`profile{}`), now extended with top-level `changes[]` and `explanation{}`
(see "Daily operation" above). `changes[]` matches the documented contract's
field name directly; the rest of the shape still differs, and we have not
rewritten it to match exactly, since it's built on the reference
implementation's own output and doing so unilaterally risked breaking
validated behaviour without confirmation of what
is actually expected. Flagging this discrepancy for clarification rather than
guessing.
